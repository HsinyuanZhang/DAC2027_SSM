# 从嵌入式 / ASIC 角度看 POSSM 类方法（侧重跨 session 适配）

> 原文：Ryoo, Krishna, Mao 等，*Generalizable, real-time neural decoding with hybrid state-space models*，NeurIPS 2025（arXiv 2506.05320v2），项目文件 `⑩POSSM - Ryoo 2025.pdf`。
> 标注约定：**【原文】** 指论文里写明的内容，附章节/图表号；**【推断】** 是我根据结构做的推理，论文里没有写；**【估算】** 是我给出的数量级估计，假设条件写在旁边，都需要你们用自己的参数复算。
> 前一个线程已经讲过 SSM 的基本原理和一般的硬件友好性，本文不再重复，直接讨论 POSSM 本身。

---

## 0. 一页结论

1. **POSSM 的计算瓶颈在权重存储，不在算力。** 单 session 规模的 POSSM-GRU 每 50 ms 大约 0.3 M MAC，相当于 ~7 MMAC/s【估算】，ASIC 很轻松就能跑完。但它有 0.47 M 参数【原文 Table 5】，INT8 下约 470 KB，比 MiBMI 整片 16.3 kB 的片上存储大约 30 倍。预训练版 o-POSSM 有 4.5–9 M 参数【原文 Table 5】，不适合放进植入端。
2. **输入交叉注意力可以改写成"事件驱动 + 查表"的形式。** 每个 spike token 只由 *unit ID* 和 *时间戳* 决定，而且 query 只有一个固定的可学习向量【原文 §2.2】。所以 LN、K/V 投影、乃至注意力打分都可以按 unit 预先算好存成表，运行时每来一个 spike 只需要读一次表、做一次 exp、再累加一次 V【推断】。这样计算量和 spike 数成正比，跟通道数无关，非常适合做成 ASIC。
3. **跨 session 适配在硬件上就是"改写一张小表"。** POSSM 的 Unit Identification（UI）冻结全部主干权重，只重新学习 unit embedding 和 session embedding，更新的参数不到 1%【原文 §2.3】，均值约 15.6 K 个【原文 Table 12】。由此可以自然地把芯片分成两块：**只读、可以放进 NVM/ROM 的冻结主干**，加上**每个 session 改写一次的小 SRAM 表**（约 10–30 KB）【推断/估算】。
4. **但 POSSM 的 UI 仍然需要反向传播。** 它要靠梯度下降训练几百个 epoch【原文 App. C.1】，放在植入端做不现实。这里正好能接上你们组 APST 的思路：APST 冻结全部权重，用闭式求解的 association profile 来生成 unit 身份。还有 SPINT 用的无标签前向 IDEncoder。**用 APST/SPINT 式的前向身份生成器替换 POSSM 的梯度式 UI**，跨 session 适配就只剩"累加充分统计量 + 一次小规模闭式求解 + 一次前向"，可以在片上或者佩戴端完成。我认为这是最值得做的研究点【推断】。
5. **延迟主要取决于 chunk 长度，计算本身几乎不占时间。** 50 ms chunk 加上事件驱动的累加，chunk 结束时只剩一步递归和读出要算。论文显示 20 ms chunk 的性能基本不掉【原文 App. D.1, Table 6】，输出查询还可以直接预测未来 50–100 ms 的行为来补偿延迟【原文 App. D.5, Table 8】。

## 1. POSSM 论文本身说了什么（只列和硬件相关的部分）

### 1.1 结构【原文 §2, Fig. 2】

| 模块 | 做什么 | 关键超参 |
|---|---|---|
| Spike tokenization | 每个 spike 表示为 `x = (UnitEmb(i), t_spike)`。unit 用可学习 embedding 表示，时间戳用 RoPE 编码的相对时间 | 维度 D；"unit"可以是单个神经元，也可以是某个通道的 multi-unit【§2.1】；去掉了 POYO 的 [START]/[END] token【App. B.1】 |
| 输入交叉注意力 | 一个 chunk 里有 N 个 spike（N 可变），用 **1 个可学习 query** `q∈R^{1×M}` 压缩成 1 个 latent `z(t)`；沿用 POYO 的 pre-LN 和 FFN | chunk T_c = 50 ms（也测过 20 ms） |
| 递归主干 | `h(t) = f_SSM(z(t), h(t−1))`，可选 S4D、GRU 或 Mamba | SS 规模：输入 64、隐状态 256、1 层；FT/o-POSSM 规模：输入 256、隐状态 512、4 层【Table 5】 |
| 输出交叉注意力 | 取最近 k = 3 个隐状态，用 P 个 query 去查询；query 由行为时间戳（RoPE）加上 **session embedding** 构成 | 一个 chunk 可以输出多个时间点，也可以预测未来时刻 |
| 读出 | 线性层 | — |

### 1.2 关键数字

- 参数量【Table 5】：S4D-SS 0.41 M，GRU-SS 0.47 M，Mamba-SS 0.68 M。FT 规模下，S4D 4.56 M，GRU 7.96 M，Mamba 8.96 M。
- 推理速度【§3.1, Fig. 4c】：在 RTX8000 GPU 上和 GRU、MLP 相当，明显快于 NDT-2 和 POYO。在 CPU（EPYC 7502）上，POSSM-SS 约 2.44 ms/chunk，o-POSSM 约 5.65 ms/chunk。**这些都是服务器级硬件上的数字，论文没有给出任何嵌入式、FPGA 或 ASIC 的数据。**
- POYO 每 50 ms 要把 1 s 窗口整体重算一遍。POSSM 每步只处理最新的 50 ms【§3.1】。这就是"流式"带来的收益。
- 精确 spike 时间很重要【App. D.6, Table 9】：H–CO 上 R² 0.835，改用 bin 级时间后降到 0.557。**这直接约束了前端设计：spike 检测器需要输出时间戳，只输出计数是不够的。**
- 把编码器换成 GRU 后效果比交叉注意力差（Table 11），但仍好于不用 spike 时间的版本。
- 论文自己说明评测**全部是离线做的**【§1】："designed for real-time … can be readily implemented"，也就是说并没有真正跑过闭环。

### 1.3 跨 session 适配【§2.3, §3.1, App. C, D.9】

| 策略 | 更新什么 | 效果 | 训练成本 |
|---|---|---|---|
| **UI**（Unit Identification） | 冻结模型，只新建并训练 unit embedding 和 session embedding（<1% 参数） | 同一只猴、隔天的数据上接近 FT；换新动物或新数据集时明显不如 FT【Table 1】 | 仍然是梯度训练，超参和 SS 模型一致（恒定学习率） |
| **FT**（全量微调） | 先做 100 个 epoch 的 UI，再解冻全部参数训 400 个 epoch | 所有设置下最好；o-POSSM-S4D(FT) 在 T–CO 上 R² 0.907，H–CO 上 0.894 | 所有权重都要可写 |
| **LoRA**（初步实验） | 用低秩适配器调 embedding | T–RT 上 0.748，UI 是 0.746；需要训练的参数 9.16 K，UI 是 15.6 K【Table 12】 | 比 UI 更快 |
| 少样本 | 只有几十个 trial 时，预训练模型 + UI 初始性能就明显更高【Fig. 4a-b】 | — | — |

还有两点值得注意：
- 训练时用了 **unit dropout**【App. C.1】，也就是随机丢掉整个 unit 的所有 spike，对通道失效有一定鲁棒性。
- 手写任务微调时，readout 层也要解冻，因为预训练数据里没有分类任务【App. C.2】。所以只换 embedding 的前提是**任务头相同**。

### 1.4 我认为对硬件不利的地方
- o-POSSM 的泛化能力是用 4–9 M 参数换来的，大模型的结果不能直接拿来说明小模型也可以【推断】。
- 语音任务没有用 spike token，而是改成"计数 + value embedding"，用了 4 个 latent、交叉注意力加自注意力、32 M 参数【§3.3, App. B.5】，和运动解码版本是两套东西。
- Mamba 版本在 UI 下表现不稳，例如 C–CO 2010 只有 0.750【Table 1】，同时它还需要输入相关的 Δ、exp 和 softplus。从硬件角度看，它是三种主干里最不划算的【推断】。

## 2. 把 POSSM 拆成硬件算子

下面以 **POSSM-GRU-SS**（D = M = 64，隐状态 256，1 层）为基准。假设 **192 通道、平均 20 Hz 的 threshold crossing**，这样每 50 ms chunk 约 N ≈ 190 个 spike【假设】。

### 2.1 前端与接口：从"计数流"改成"事件流"
- 每个事件 = 通道 ID（8–9 bit）+ chunk 内时间戳（50 ms 以 1 ms 分辨率计，6 bit）≈ 15 bit。
- 事件码率约 190 × 15 bit / 50 ms ≈ **57 kb/s**【估算】。作为对照，MiBMI 192 通道 10 ms 计数是 192 kb/s，经 DNC 压缩后 39.7 kb/s（MiBMI 论文）。所以事件流本身并不贵。
- 时间戳分辨率（1/2/5 ms）对 R² 的影响是一个值得扫的硬件参数（Table 9 只比较了"精确"和"bin 级"两个极端）。

### 2.2 输入交叉注意力：事件驱动的"查表 + 在线 softmax"【推断，重点】

原文的计算是 `K = X W_k`、`V = X W_v`，再加 RoPE 和 softmax。按字面实现，每个 spike 要做两次 64×64 投影，约 8 K MAC，每个 chunk 约 1.6 M MAC。

但注意三点：
1. token 的内容部分**只有** `UnitEmb(i)`，时间只通过 RoPE 进来（§2.1）。pre-LN 作用在 `UnitEmb(i)` 上，所以对每个 unit 来说 `LN(UnitEmb(i))·W_k` 和 `·W_v` 都是**常数**。
2. query 是**单个固定**的可学习向量。
3. RoPE 是按维度成对的旋转，打分只依赖 unit i 和相对时间 Δt。

所以可以一路预计算下去：
- **K/V 表**：每个 unit 存一份 `k_i`、`v_i`。192 × 128 × 8 bit ≈ **24 KB**。
- **打分表**：时间戳量化到 1 ms 时，Δt 在一个 chunk 里只有约 50 种取值。可以直接存 `score[i][Δt] = q·R(Δt)k_i`，192 × 50 × 8 bit ≈ **9.6 KB**。多头时乘以头数。
- 运行时每个 spike 的操作：读一次打分表 → exp 查表 → 用在线 softmax（FlashAttention 式的 running max/sum）更新 → 累加 `e^s · v_i`（64 次乘加）。如果实现里对 value 也做了 RoPE（POYO 的实现里可能有，**需要对照代码确认**），还要再加一次 64 维旋转。
- 每个 chunk 约 190 × ~130 ≈ **25 K 次操作**，比按字面实现少 50 倍以上【估算】。chunk 结束时做一次除法和 LN，再经过一个 64→256→64 的 FFN（约 32 K MAC）。

这个改写有几个硬件上的好处：
- **计算量 ∝ spike 数**。没有 spike 的通道不产生任何计算，失效通道也不需要特殊处理。这和训练时的 unit dropout 正好匹配。
- **跨 session 适配 = 重新生成这几张表**（见 §3）。
- 这个改写只在"单 query + 内容只依赖 unit ID"的前提下成立。改成多 latent（比如语音版的 4 个）或在 token 里加入幅度、波形特征，表的规模会线性增长，但仍然可行。

### 2.3 递归主干选型

| 主干 | 每步计算（SS 规模） | 硬件特性 | 论文表现 |
|---|---|---|---|
| **GRU** | 3×(64×256 + 256×256) ≈ 246 K MAC | 稠密矩阵-向量乘，σ/tanh 查表；状态 256 维，非线性递推的量化行为比较成熟 | SS 和 UI 下普遍最稳；handwriting 从头训练时最好 |
| **S4D** | 对角复数递推 O(H·N_state)，主要开销在 H×H 的混合线性层 | Ā 可以离线算好，递推本身是逐元素运算；**LTI 结构易于做定点误差分析**，但特征值 |λ| 接近 1 时状态精度会成为问题 | 参数最少（0.41 M）；**FT 在新动物、新数据集上最好**（T–CO 0.907，H–CO 0.894） |
| Mamba | 需要输入相关的 Δ/B/C、exp、softplus | 非线性多、数据依赖强，硬件最不友好 | 参数最多，UI 表现不稳定 |

建议：植入端优先考虑 **S4D**（结构可分析、参数少），或者用 GRU 作为稳妥基线。也可以试 minGRU 这类去掉 `U·h` 稠密项的线性递归变体，把每步的 256×256 乘法去掉。这一点论文没有测过，属于【推断】。

### 2.4 输出端
- 只有 k = 3 个隐状态（256 维）作为 K/V。query 由 session embedding 和行为时间戳构成，可以**按 session 预先算好**。每个输出点只要做 3 个打分、一个 3 元 softmax 和一个 256 维加权和，再接一个 256→2 的读出层，总共约 1–2 K MAC【估算】。
- 状态缓存：3 × 256 × 16 bit = 1.5 KB。作为对照，APST 的 4 层滑窗 KV cache 是 4 × w × 256 × 2 个数，POYO 需要缓存整个 1 s 窗口的 spike。

### 2.5 总账【估算】

| 项目 | POSSM-GRU-SS | o-POSSM-GRU | 参考：MiBMI（JSSC 2024） |
|---|---|---|---|
| 计算 / chunk | ≈ 0.3 M MAC（主要是 GRU） | ≈ 4–6 M MAC（4 层 512 维） | LDA，极低 |
| 计算速率（20 chunk/s） | ≈ 7 MMAC/s | ≈ 100 MMAC/s | — |
| 权重（INT8） | ≈ 470 KB；INT4 ≈ 235 KB | ≈ 8 MB | 16.3 kB |
| 每 session 可写表 | ≈ 12 KB embedding + 24 KB K/V + 10 KB 打分表 | 同量级 × 4 | DNC 索引 + LDA 权重（离线训练） |
| 动态功耗量级（1–5 pJ/MAC，含 SRAM） | ≈ 7–35 µW | ≈ 0.1–0.5 mW | 整片 883 µW（含 192 通道记录） |

结论：**SS 规模的 POSSM 在算力和功耗上可以放进植入端，难点是存储面积和漏电。** 470 KB SRAM 在 65 nm 下要占几个 mm²，已经超过 MiBMI 整片的 2.46 mm²。所以权重压缩（INT4 / 剪枝 / 结构化低秩）和权重介质（ROM / NVM）是一阶问题。o-POSSM 规模适合放在佩戴端 SoC 或边缘 NPU 上。

### 2.6 延迟
- 系统延迟 ≈ chunk 长度 + 尾部计算。采用事件驱动累加时，chunk 内的工作在 spike 到达时就已经完成，chunk 结束后只剩一步递归和读出，在 MHz 级时钟下是微秒量级【估算】。论文给出的 CPU 毫秒级数字在 ASIC 上并不是瓶颈。
- 想降低感知延迟，有两条路：20 ms chunk（Table 6 显示性能基本持平），或者用输出 query 预测 +50 ms 的行为（Table 8，R² 只降 0.005–0.02）。后者在硬件上几乎没有额外成本，因为只是改一下 query 的时间戳。

## 3. 跨 session 适配的硬件视角（重点）

### 3.1 POSSM 的结构天然把参数分成"冻结"和"可写"两类

| 类别 | 内容 | 大小（SS 规模） | 更新频率 | 适合的介质 |
|---|---|---|---|---|
| 冻结主干 | W_k/W_v/q（压缩成表之前）、FFN、SSM/GRU、输出注意力、readout | 数百 KB | 出厂或预训练时一次 | **ROM / eFlash / RRAM 存内计算** |
| Session 状态 | unit embedding → K/V 表、打分表；session embedding → 输出 query | 数十 KB | 每次校准（每天或每次漂移） | SRAM（或者可写 NVM） |
| 运行状态 | 在线 softmax 累加器、h(t)、最近 3 个 h | 约 2 KB | 每 chunk | 寄存器 / 小 SRAM |

【推断】这种划分让**主干权重永远不用改写**，因此很适合 NVM 或存内计算。RRAM 的写入耐久度和写能耗是它的弱点，但"只读"的工作负载正好绕开了这个问题。这和你们合作方 SUSTech 王中锐老师组的忆阻器/存内计算方向可以直接对接，具体工艺要和他们确认。可写部分只有几十 KB 的 SRAM，跨 session 重写的代价是 **"数十 KB 的写入"**，而不是重新烧录整个模型。

### 3.2 四种适配方式的硬件代价对比【推断/估算】

| 方式 | 需要的数据 | 运算类型 | 能否在植入端完成 | 写入量 | 预期精度（依据） |
|---|---|---|---|---|---|
| **FT**（POSSM） | 带标签的校准 trial | 全模型反向传播，数百 epoch | 否：需要高精度梯度、激活缓存，而且全部权重必须可写 | 全部权重（数百 KB–MB） | 最好（Table 1） |
| **UI / LoRA**（POSSM） | 带标签的校准 trial | 通过冻结模型做反向传播，只更新 embedding | 不现实：BPTT 要缓存 20 个 chunk 的激活和门控，而且需要 FP16 级精度的反向数据通路；**适合放在佩戴端或手机** | 15.6 K / 9.16 K 参数（Table 12）→ 再生成表 | 同一动物接近 FT，跨动物差一截 |
| **SPINT 式**（无标签、无梯度） | 少量无标签校准数据 | IDEncoder 一次前向（逐 trial 的 MLP + 池化） | 可以：只需要前向 MLP 和统计池化 | 每个 unit 一个 embedding | FALCON 上 M1 0.66、M2 0.26、H1 0.29（SPINT/APST 论文 Table 1） |
| **APST 式**（有标签、闭式、无梯度） | 少量带标签校准 trial | 每个 unit 一次小规模岭回归（如 3×3 方向调谐）+ 一次前向 MLP/FiLM | 可以：本质是**充分统计量累加 + 极小矩阵求解** | 每个 unit 一个 profile 和 identity | FALCON 上 M1 0.65、M2 0.42、H1 0.44，H1 和 RNN 私有标签 oracle 持平（APST Table 1） |

**关键观察**：
- POSSM 的 UI 和 APST/SPINT 想解决的是同一个问题：**为新 session 的每个 unit 生成身份向量，主干不动**。区别只是"怎么生成"：POSSM 用梯度下降去优化，APST/SPINT 用前向网络（摊销推断）直接输出。从硬件角度看，后者是数量级上更便宜的选择。
- APST 的论点是"无标签数据看不出 tuning 漂移"，这对 POSSM 同样成立。POSSM 的 UI 之所以有效，正是因为它用到了行为标签，只不过是通过梯度用上的。APST 的闭式 profile 是把"用标签"这件事做成了硬件可实现的形式。

### 3.3 推荐路线：POSSM 主干 + APST 式闭式身份生成器（"APST-SSM"）【推断，可作为研究课题】

```
校准阶段（每个 session 一次，前向和闭式运算，无反向传播）
  事件流 + 行为标签 ──► 统计累加器：每个 unit 的 Σr、Σr·cosθ、Σr·sinθ、Σr²、计数…
                     ──► 每个 unit 解 3×3（或 K 维 + SVD 投影）岭回归 → association profile p_u
                     ──► 活动签名 h_u（逐 trial 的 ReLU 层 + 平均）
                     ──► 冻结的身份网络 g(FiLM(h_u, p_u)) → UnitEmb_u
                     ──► 冻结的 W_k、W_v、q → 重新生成 K/V 表和打分表（写入 SRAM）
运行阶段
  事件 ──► 查表打分 → exp → 在线 softmax 累加 ──► z(t) ──► S4D/GRU ──► 输出注意力 ──► 速度
```

这个组合把三件事放在了一起：
- **POSSM**：spike 级 token、单 query 编码器、O(1) 的递归状态，适合流式运行和事件驱动。
- **APST**：冻结全部权重，用少量带标签 trial 的闭式 profile 完成适配，没有目标域梯度。
- **SPINT**：可以作为无标签时的退路，或者和 profile 拼接使用。

和 APST 现在的 set-temporal transformer 相比，主要差别在两处：一是用 SSM 替换 4 层滑窗因果 transformer，把 KV cache 换成固定大小的状态；二是用 spike 级时间戳替换 20 ms bin 加 Conv1d。需要验证这两处替换会不会损失 APST 在 FALCON 上的精度。我对这一点没有把握，需要做实验。

### 3.4 片上校准引擎（如果要在植入端做适配）【推断】
- **累加器阵列**：每个通道若干个 16–24 bit 累加器（计数、按方向加权的和、平方和）。只在校准窗口里打开，硬件就是"MAC + 门控"。
- **小规模求解器**：每个 unit 解一个 3×3 或 4×4 对称正定系统。可以用 Cholesky 或闭式求逆。192 个 unit 串行处理，每个几百次运算。
- **身份网络前向**：复用推理用的 MAC 阵列。
- **表重建**：每个 unit 计算 `LN(e_u)·W_k`、`·W_v` 和 50 个打分。192 × (2×64×64 + 50×64) ≈ 2.2 M MAC，在毫秒量级内完成【估算】。
- 校准一次的总能耗大约在 µJ 量级【估算】。相比之下，梯度式 UI 每次是"数百 epoch × 数十 trial × 20 chunk × 前向+反向"，大约在 10¹⁰–10¹¹ MAC 量级，而且需要更高精度的数据通路。

### 3.5 什么时候重新校准：片上漂移检测【推断】
- 便宜的监测量有：各通道放电率的滑动均值和方差；输入注意力权重的熵或分布（新增或丢失的 unit 会让注意力分布明显变化）；隐状态 h(t) 的统计量和预训练时的统计量之间的距离。
- 超过阈值时，通过无线链路请求一次带标签的校准，比如提示用户做一组 cued movement（APST 和 FALCON 的设定都假设临床上有这样的校准）。实在没有标签时，先退到 SPINT 式的无标签身份生成。

### 3.6 Unit 的定义：在芯片上用通道，不用 sorted unit
POSSM 允许 "unit" 是通道级 multi-unit【§2.1】，FALCON 和 APST 用的也是未分选的 threshold crossing。片上做 spike sorting 很贵，所以建议**以通道为 unit**。由此带来的好处是 unit 表的大小在出厂时就确定了（等于通道数），跨 session 时不需要动态分配表项，只改内容。少数通道上有多个 unit 时，可以考虑"每通道 2 个模板"之类的轻量扩展（MiBMI 引用的 dual spike detector 属于这个方向）。

## 4. 系统划分方案

| 方案 | 植入端 | 佩戴端/外部 | 无线码率 | 适配在哪里做 | 适用场景 |
|---|---|---|---|---|---|
| **A 全植入** | 前端 + 事件检测 + 整个 POSSM-SS（NVM 主干 + SRAM 表） | 只做显示和控制 | 很低（只传输出） | APST 式闭式适配在片上；或者佩戴端算好后写回 SRAM 表 | 长期全植入，功耗预算在 sub-mW |
| **B 编码器在植入端** | 前端 + 事件驱动交叉注意力，每个 chunk 输出 z(t) | SSM 主干 + 读出 + 适配 | 64 维 × 8 bit / 50 ms ≈ **10 kb/s**，比原始事件流的约 57 kb/s 更低【估算】 | 佩戴端算好 unit 表后写回植入端 | 无线带宽紧张时，用学到的编码器当压缩器 |
| **C 植入端只做感知** | 前端 + 事件检测，输出事件流 | 完整的 o-POSSM（MB 级），可以用梯度式 UI/LoRA | 约 57 kb/s | 佩戴端，可以做反向传播 | 需要预训练大模型的泛化能力 |

我的倾向是：**先做 B 或 C，验证大模型和适配算法，把 A 作为长期目标。** B 的分界点很有意思，因为输入交叉注意力正好是"依赖 session 的那部分"，而主干是"session 无关的部分"。不过这也意味着适配时植入端的表需要更新【推断】。

## 5. 建议的研究路线和实验

**阶段 1：软件复现，建立硬件感知的基线**
- 复现 POSSM-SS（S4D/GRU）。论文说代码会通过 `torch_brain` 发布，但 UniBCI 写作时还没有公开代码。**是否已经开源需要你们自己确认。** 论文没有用 FALCON；建议在 FALCON M1/M2/H1 上补测，这样能和 SPINT、APST、NDT2 直接对比。
- 实现 §2.2 的"查表 + 在线 softmax"等价改写，验证数值上和原实现一致。

**阶段 2：硬件约束下的消融**（每一项都对应一个硬件参数）
- 时间戳分辨率：1 / 2 / 5 / 10 ms。
- chunk 长度：10 / 20 / 50 ms；k（缓存的隐状态数）：1 / 2 / 3。
- 量化：权重 INT8/INT4，状态 INT16/INT12，打分表 6/8 bit，exp 查表位宽。
- 主干：S4D vs GRU vs minGRU / 线性递归；隐状态维度 64 / 128 / 256。
- 模型规模：从 o-POSSM 蒸馏到 SS 规模后，跨 session 能保留多少。

**阶段 3：适配方式对比**（核心创新点）
- 同一主干上对比四种适配：FT、UI(梯度)、LoRA、SPINT 式、APST 式（APST-SSM）。
- 评价时除了 R²，还要报告**适配成本**：需要的 trial 数（4/8/16/32，和 APST 一致）、写入的字节数、校准的 MAC 数和所需精度、能否只用前向完成。这样"精度 vs 适配成本"就能画成 Pareto 图，这类图在现有论文里还比较少【推断】。

**阶段 4：硬件**
- RTL 实现三个引擎：事件驱动的注意力累加器、递归主干的 MAC 阵列、校准统计引擎。先上 FPGA 跑 FALCON 回放，测功耗和延迟，再考虑流片。
- 权重介质对比：SRAM vs ROM vs RRAM（如果和王老师组合作的话），比较面积、漏电和精度。

**可能的论文切入点**【推断】
1. "梯度自由、硬件原生的跨 session 适配"：APST profile 加上 SSM 主干，再加上查表式编码器。
2. 事件驱动的 spike-token 交叉注意力加速器：计算量 ∝ spike 数，并给出精度和时间戳分辨率的关系。
3. "冻结主干 NVM + 可写 session 表"的存储架构，以及漂移触发的校准机制。

## 6. 风险与开放问题
- **小模型能不能泛化**：POSSM 最好的跨动物、跨数据集结果来自 4–9 M 参数的 FT 模型。SS 规模 + 无梯度适配在新动物上能做到多好，目前还不知道（APST 在 FALCON 上的结果给了一些乐观的信号）。
- **离线 vs 闭环**：POSSM 和 APST 都只在离线数据上评测过。闭环下用户会适应解码器，漂移和误差累积的表现可能不一样。
- **长时间递归的稳定性**：训练序列是 1 s，测试 trial 长 3–5 倍【§3.1】，在连续运行数小时的场景下，状态会不会漂移、需不需要周期性复位，都要验证。定点实现会让这个问题更突出。
- **任务头**：换任务（例如从速度解码换到分类）时 readout 也要重训【App. C.2】，"只换表"的假设就不成立了。
- **RoPE 是否作用在 V 上、LN 的确切位置**等实现细节决定了 §2.2 的改写是否严格等价，需要对照代码确认。

## 附：与项目内其他论文的关系
- **⑨POYO**：POSSM 的编码器、tokenization 和 UI 都来自 POYO。区别是 POSSM 改成了 50 ms chunk、1 个 latent 加递归，不再每步重算 1 s 窗口。
- **①SPINT**：无标签、无梯度的 IDEncoder，可以直接作为 POSSM 的"身份生成器"替代品。它的上下文相关位置编码和 POSSM 的 unit embedding 本质上是同一类东西。
- **2609.39080（APST，你们组）**：闭式 association profile 加冻结权重，是本文 §3.3 推荐路线的核心。主要差异是时间主干（滑窗 transformer vs SSM）和输入粒度（20 ms bin vs spike 时间戳）。
- **⑧MiBMI**：给出了植入端的预算参照：65 nm、2.46 mm²、883 µW、16.3 kB 存储、权重离线训练。和 POSSM-SS 相比，存储差约 30 倍。
- **⑥FALCON**：建议作为统一的跨 session 评测平台，它提供少量带标签校准 trial，还报告归一化延迟。
- **②NDT2 / ③UniBCI**：Transformer 类的预训练基线。UniBCI 提到 POSSM 时说它没有公开代码，所以没有放进对比实验。
