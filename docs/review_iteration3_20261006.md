# 第三轮审核：审核修复之后的进展、结论修正与下一步（2026-10-06）

审核范围：提交 `2c62872..7c07d8c`，即上一轮审核修复（e142342）、K=10 合规重跑与 ui_prior（9f317a3）、Track E v2 重建（7c07d8c），以及更新后的阶段文档。依据：后台代码审查（15 项，全量测试 288 项通过、1 项失败）、对 manifest 和结果文件的直接核查、APST 的选择记录。

## 0. 结论先行

1. **这一轮的主线进展是真实的。**
   - AP 骨架在 K=10 下按规则延长预算：2000 → 16000 步，source 验证 0.629 → 0.715。之前所有基于 2000 步骨架的结论都应视为训练不足。
   - Track A 合规重跑后，结果随标签数单调，两个 target 之间也稳定了，印证了上一轮“不可识别 + 未收敛”的诊断。
   - **“先验 + 梯度”（ui_prior）是这一轮最有价值的结果**：8 个 trial 为 0.569，33 个 trial 为 0.657。
2. **这些结论需要降级或补证据：**
   - ui_prior 只有 2 个 target、1 个 seed；ui_grad 自己随标签数非单调（0616 上 4 个 trial 0.416，8 个 trial 0.165）。
   - “组合形式通过门槛 4.2.5”是事后放宽了门槛的定义；而且 ui_prior 需要在 target 端做梯度，属于片外 L2 层，不是片上闭式方法。
   - APST 在 dev 上的参考数字（dual-site 0.843，ACT-only 0.693）来自按 dev R² 选出的 checkpoint（规则为 `earliest_max_equal_session_dev_r2`），是偏乐观的上界。“ui_prior 处在 ACT-only 水平、与 APST 差约 0.19”高估了差距。无偏的 APST 参考只有 final split 上的 0.808 和 0.578。
3. **Track E v2 的“source 拟合门槛未通过”，是文档的人工判断，不是脚本做出的判断。** 脚本里的门槛取被评测 checkpoint 自己的分数减 0.05，永远会通过；实际挡住 target 评测的是预算规则。
4. **Track E 有一个新发现的训练缺陷，可能是它卡在 0.607 的重要原因**：训练窗口全部结束在每个 trial 的最后一个 bin（`lo` 算出来没有使用），训练只看过每个 trial 末尾的 128 个 bin，验证却覆盖所有端点。另外，蒸馏目标与 unit dropout 的重归一化不匹配，会让学到的表系统性偏小（约 0.7 倍）。
5. **几项修复的落地形式抵消了修复本身的目的**：门槛形同虚设；单位检查区间过窄，或者一出错就中止整个评测；B6 只在 set 评测里修了。测试套件当前有 1 项失败。

## 4. 对下一轮的启发

### 4.1 Track E：先修训练，再判断思路

在 source 上 0.607 对 0.715 的差距，至少混合了三个因素：A1 的窗口采样、A4 的蒸馏偏差，以及“描述到表”这个映射本身的表达能力。建议按顺序处理：

1. **修复 A1 和 A4**，然后在同一预算下重跑。这一步只需修代码，不必改配方。
2. **用一个诊断把剩余差距拆开**：用一个不受 softmax 结构约束的回归器（例如 MLP），从描述回归各 source session 的 AP 表，再用重建出来的表在 source 上解码。
   - 如果重建表能接近 0.715，说明描述里的信息足够，限制来自 E1 的折叠结构；
   - 如果也上不去，说明描述的信息不够，应优先引入 T4（CO 任务有目标方向）和更强的活动编码器。
3. 门槛（A2）改为与 AP 骨架的分数比较，并加单元测试，保证门槛确实会失败。

### 4.2 ui_prior：从“初步证据”变成可靠结论

1. 每个预算至少 3 个 seed，同时报告均值和方差。
2. 用 000688 的月级和年级间隔分层，确认“8 个 trial ≈ 33 个 trial”是否在更大的漂移下仍然成立。
3. 把它定位为片外 L2 层的标签效率方法（只需几百个参数的梯度，可以在外部计算机上几秒完成），与片上闭式方法分开报告。
4. 如果它在更大的间隔下依然成立，可以进一步研究：先验表能否由 Track E 提供，也就是“集合先验 + 少量梯度”。

### 4.3 与 APST 的公平比较

1. 在 APST 那边，按不看 dev query 的规则重新选 checkpoint（例如用 source 验证集，或固定训练步数），得到无偏的 dev 参考。
2. 或者，等我们的方法定型后，双方都按协议在 final split 上各评测一次。

### 4.4 工程

1. 把单位检查、source 门槛、预算检查抽成一个共享模块：两个评测入口用同一套区间；越界时记录到行里，而不是中止整次评测；结果逐行写入。
2. 延长预算的循环比较实际训练步数和预算；参数改变时使用新目录；最后一档仍未收敛时如实报告“未收敛”。
3. 先让测试套件全部通过，再产出结果。
